Failure modes & mitigations — Core tier, scoped to Parfumado

CP-01

Warehouse & Modeling (Snowflake / dbt)

  • GrainSubscription order data modeled at the wrong grain — order-line vs. subscription-cycle — causes recurring-revenue numbers to double- or under-count renewals.
  • LogicMetric logic gets built ad hoc per analyst request, so Finance and Marketing dashboards quietly diverge on the same number.
  • GrainDefine grain explicitly as a tested dbt model before any metric is built on it — the same star/snowflake-schema discipline used designing the AVON EDW in Redshift.
  • LogicCentralize metric logic in a semantic layer that Tableau reads from, mirroring the view/stored-proc semantic layer built at AVON.
CP-05

Event Streams (GA4 / Segment)

  • SchemaGA4/Segment event schemas change without notice — a new app version, a new tracking plan — silently breaking downstream funnel and churn models.
  • VolumeEvent volume spikes around promotions or subscription-box launches overload ingestion and create customer-journey gaps exactly when they matter most.
  • SchemaTreat every tracking-plan change as a breaking-change review with schema validation — the same discipline applied to the ADMIRAL clickstream pipeline at millions of events/day.
  • VolumeLoad-test ingestion ahead of known spikes rather than discovering the ceiling live, informed by running the Kafka/Kinesis pipeline that already handled this exact class of volume.
CP-06

Data Quality

  • BillingFailed or retried subscription payments get miscounted as both a charge and a churn event, corrupting MRR until Finance's numbers stop reconciling.
  • FatigueChecks pass technically but nobody owns triaging failures, so alerts pile up and get ignored — the rule-fatigue pattern that lets real issues slip through.
  • BillingBuild a specific reconciliation check for payment-retry states against churn logic — the same category of validation-rule design used across 100+ datasets with Great Expectations at PFIZER.
  • FatigueRoute data-quality alerts to a named owner with a defined SLA, not a shared channel — the same proactive-catch-before-downstream principle behind the PFIZER work.
CP-08

Dashboards (Tableau)

  • DriftCohort/LTV calculations get rebuilt slightly differently in Tableau calculated fields versus the dbt layer, so two dashboards disagree on the same cohort.
  • SprawlDashboards proliferate per stakeholder request with no owner, and a stale one gets read as current right when a channel underperforms.
  • DriftPush all metric logic into dbt and keep Tableau strictly presentation-layer — the same self-service-BI-on-top-of-a-governed-lake pattern built for the Real Estate/CRM project's 50+ users.
  • SprawlApply an ownership and refresh-cadence standard to every published dashboard, extending the region/country/plan-level reporting discipline built at TIREHUB.
CP-09

Recommenders / ML Serving

  • SkewA "next scent" recommendation model trained offline behaves differently once served live against real browsing sessions — training/serving skew.
  • SkewApply the same discipline behind the Real Estate/CRM recommender build — feature computation shared between the training path and the serving path, not two parallel implementations.
CP-11

Single Customer View (Commerce / Billing / CRM / Ads)

  • IdentityThe same customer exists as separate records across the commerce platform, subscription billing, CRM, and ad platforms, so churn and LTV get calculated on an incomplete view of any one customer.
  • IdentityBuild customer-identity resolution as an explicit modeling step, not an assumed join key — extending the MDM principles established across 6+ enterprise datasets at AVON to Parfumado's commerce/billing/CRM/ads sources.

Failure modes

  • CP-01.2SCD Type-2 logic done wrong corrupts history silently — no error is thrown, the past just becomes wrong.
  • CP-01.2Grain mismatches between fact tables produce fan-out joins that look plausible but double-count.
  • CP-01.3Business logic duplicated across dbt, the BI tool, and stored procs — three sources of truth for one metric.
  • CP-01.4/.5Unbounded ad hoc query access with no workload management blows up warehouse cost.

Mitigation & leadership signal

  • CP-01.2Pre-merge dbt tests asserting row counts and key uniqueness on every SCD-2 table, so history-breaking changes fail CI instead of surfacing as an unexplained number months later.
  • CP-01.2Document and test fact-table grain explicitly, with join-key cardinality checks required before a new fact table merges.
  • CP-01.3Consolidate metric logic into one semantic layer that every BI tool and report reads from — collapses three sources of truth into one.
  • CP-01.4/.5Workload management with query cost limits and a self-service tier separate from ad hoc — makes cost control a designed feature, not a policy memo.

Failure modes

  • CP-02.2The small-file problem — too many tiny objects — tanks query performance over time.
  • CP-02.3Schema evolution breaks downstream consumers when there's no contract enforcement between zones.
  • CP-02.5Crawler-inferred catalog drifts from what the data actually looks like.
  • CP-02.2No ACID guarantees on raw Parquet/S3 means a partial write corrupts a partition silently.
  • CP-02.5Permission sprawl at the lake level — looser and harder to audit than warehouse RBAC.

Mitigation & leadership signal

  • CP-02.2Scheduled compaction jobs with partition-size targets enforced at write time, not cleanup after the fact.
  • CP-02.3Schema contracts declared by writers and validated by the catalog at ingest, so evolution is negotiated, not discovered downstream.
  • CP-02.5Contract-based schema registration instead of crawler inference — the catalog reflects what was promised, not what was scraped.
  • CP-02.2Adopt a transactional table format (Delta/Iceberg/Hudi) for any zone with concurrent writers, closing the partial-write gap structurally.
  • CP-02.5Centralize lake access through a governed catalog layer instead of raw bucket policies, making permissions auditable in one place.

Failure modes

  • CP-03.2Concurrent-writer conflicts when two jobs touch the same table at once.
  • CP-03.4Autoscaling misconfiguration causes either cost spikes or job starvation, rarely something in between.
  • CP-03.3Hive-metastore-to-Unity-Catalog migration is more involved than the marketing implies.
  • CP-03.2Unbounded time-travel retention quietly inflates storage cost.

Mitigation & leadership signal

  • CP-03.2Partition high-concurrency tables to isolate writers, or move to structured-streaming merges that serialize safely.
  • CP-03.4Right-size clusters from workload profiling before setting scaling policy, then revisit quarterly — proactive sizing beats reactive tuning after a bill shock.
  • CP-03.3Run the metastore migration as its own phased project with a parallel-validation period, not a weekend cutover.
  • CP-03.2Set explicit time-travel retention windows per table tier tied to actual audit/compliance need, not defaults.
